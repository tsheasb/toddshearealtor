## Required build.py patch (not yet applied to the live repo)

The original `inline()` function only supported links, bold, and italic — no images. Issue 01 needed listing photos, IG follow photos, and other body images, so this line was added:

```python
def inline(t):
    t = html.escape(t, quote=False)
    t = re.sub(r"!\[([^\]]*)\]\(([^)]+)\)", r'<img src="\2" alt="\1" loading="lazy">', t)  # ADD THIS LINE
    t = re.sub(r"\[([^\]]+)\]\(([^)]+)\)", r'<a href="\2">\1</a>', t)
    t = re.sub(r"\*\*([^*]+)\*\*", r"<strong>\1</strong>", t)
    t = re.sub(r"(?<!\*)\*([^*]+)\*(?!\*)", r"<em>\1</em>", t)
    return t
```

The new line **must** come before the link regex — image syntax (`![alt](url)`) would otherwise get partially matched by the link pattern first.

This means `![alt text](image-url)` now works anywhere in the post body, same as `[link text](url)` already did.

## Required CSS patch (not yet applied to the live repo)

Body images had no styling at all — they rendered at full pixel width (e.g., a 2048px-wide MLS photo) and overflowed the ~72ch article column instead of scaling to fit. Add this to `css/components.css`, right after the existing `.article__hero` rules:

```css
.article p img {
  display: block;
  width: 100%;
  height: auto;
  max-width: 100%;
  margin: 1.5rem auto;
  border-radius: 12px;
}
```

This does not affect the dedicated hero image — that already had its own working rule (`.article__hero img`).

## How to write a new issue

Create a new file in `posts/` named:

```
YYYY-MM-DD-your-slug-here.md
```

**The filename IS the URL slug** (minus the date prefix). No separate `slug` front-matter field exists — whatever you name the file becomes `/posts/your-slug-here.html`. Pick the filename with the primary SEO keyword in mind.

### Front matter (top of file, between `---` lines)

```yaml
---
title: Issue Title Here
date: 2026-07-22
number: 1
teaser: One-line teaser — this is ALSO the meta description and RSS description.
hero: /assets/posts/issue-01-hero.jpg
hero_alt: Alt text for the hero image
---
```

| Field | Used for | Notes |
|---|---|---|
| `title` | `<title>` tag, H1, RSS item title | |
| `date` | Sort order, display date | Format `YYYY-MM-DD` |
| `number` | Issue number badge ("No. 001") | Integer |
| `teaser` | **Meta description AND RSS description** | One field does both jobs — keep it under ~155 characters if you want it working well for SEO |
| `hero` | Hero image path | See the hero template reference doc for the standard format |
| `hero_alt` | Hero image alt text | Only the hero gets alt text — no per-body-image alt field beyond the markdown `![alt](url)` syntax itself |

### Body sections (standard template, in order) — with locked-in blurbs

Every `##` section gets a one-line italic blurb right underneath it, evergreen across issues (doesn't change even though the market/listings/content does). These were locked in on issue 01:

```markdown
Opening line — short, confident, salty. Sets up the issue.

## The Nitty Gritty
*This issue's market, by the numbers.*
Market stats intro + bullet list (median price, DOM, inventory, etc.)
[Per-issue scope note goes here, e.g. "Stats reflect single-family homes in
the City of X only — not condos, not the wider county."]

## My Listings
OPTIONAL — only include this section when Todd has active listings to feature.
When omitted, leave it out entirely: no placeholder text, no "check back soon."
Sits between The Nitty Gritty and Window Shopping — Todd's own listings come
before other agents' listings, always. Needs its own blurb once first used —
not yet written since it hasn't appeared in an issue yet. Suggest something
like *What's currently on the market with me* when it's needed.

## Window Shopping
*Some listings that caught my eye this issue.*
Intro line, then one paragraph per listing, with a photo:
**Address — $Price**
![alt text](photo-url)
Note about why it's worth a look. Beds/baths/sqft, listing courtesy of
[Agent Name], [Office]. (MLS #XX-XXXX)
Non-Todd listings need: agent name + office name attribution, MLS number,
photo, and the "not my listings" disclaimer under the CTA at the end of
the section (see issue 01 for exact wording).

## This Issue's Vibe
*Local adventurers, storytellers, eats & other must-follows.*
Follow / listening / reading (now "Currently Obsessed With"), condensed.

**Follow:** [@handle](url)
![photo](url)
Blurb about the place/account.

(repeat for each IG follow, usually 1-2)

**House Radio**
*The soundtrack to the SB Residency, updated all the time.*
![cover art](spotify-cover-url)
Everything we're listening to here in Santa Barbara, updated all the time.
[Listen on Spotify](playlist-url)
On repeat this issue: [specific pick, artist, one line on why]

**Currently Obsessed With: [topic]**
*Whatever's got my attention this cycle — tool, trend, or otherwise.*
![photo](url — Todd's own screenshot/photo, NOT a third-party company's
logo/trademark, to avoid implied-endorsement issues]
1-3 sentences on what it is and why it matters right now.

## Ready When You Are
*Buying, selling, or just curious what it's worth — I'm here.*
CTA.
```

Markdown support in `build.py` is minimal: `##` headers, `**bold**`, `*italic*`, `[link](url)`, `![alt](url)` (as of the v3 patch above), `- ` bullet lists, and paragraphs. No H3, no tables.

## What's NOT wired up (gaps to know about)

- **No separate SEO meta description field** — reuses `teaser`. If a punchier teaser and a keyword-optimized meta description ever need to diverge, `build.py` needs a new field added.
- **No slug override field** — slug is always derived from the filename.
- **No alt text field separate from markdown syntax** — body images get their alt text from `![alt text here](url)` directly; no separate front-matter field for it (unlike the hero, which has `hero_alt`).
- **No OG tags, canonical URL, or meta keywords** — bare-bones head, nothing to break but nothing extra for social previews either.
- **No conditional-section logic** — "My Listings" being optional is a content decision (include the `## My Listings` block or don't), not something `build.py` enforces or auto-detects. Whoever's writing the issue has to remember to add/remove it.
- **Body image sizing is uniform** — every body image gets the same treatment (full column width, 12px rounded corners). No way to do side-by-side photos, galleries, or different sizes without a further CSS/build.py change.

## Publishing checklist

1. Apply the build.py and CSS patches above if they haven't been applied to the live repo yet (one-time; check `scripts/build.py`'s `inline()` function and `css/components.css` to see if they're already there).
2. Write the post as `posts/YYYY-MM-DD-slug.md` with correct front matter and the locked-in section blurbs.
3. Include `## My Listings` only if Todd has active listings this cycle.
4. Run `python3 scripts/build.py` — regenerates the post HTML, `rss.xml`, and the issue lists on `residency.html` / `index.html`. Watch for the "issue-list container not found" warning — if it appears, the issue list on those pages didn't update and needs a manual check.
5. Commit + push to `main` — GitHub Pages serves straight from the branch.
6. Mailchimp's RSS-Driven Campaign (Audience ID `90c669fbd4`) picks up the new `rss.xml` entry on its biweekly schedule and sends automatically — **no manual campaign creation needed**, that's the whole point of this setup.
7. BHHS formal compliance review is optional per Todd's direction (7/29/26) — the standing safeguards are: agent-name + office attribution on every non-Todd listing, MLS number cited, and the "not my listings" disclaimer under the Window Shopping CTA.

**Don't push/publish without Todd's explicit go-ahead**, per standing project instructions.
