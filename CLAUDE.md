# SB Residency — Claude Code Operating Instructions

This file governs how Claude Code should build and deploy issues of Todd Shea's
"SB Residency" newsletter/blog. Read this in full before touching the repo or
the Mailchimp campaign.

## What this project is

- Public content marketing blog + biweekly newsletter for Todd Shea, REALTOR®
  at Berkshire Hathaway HomeServices California Properties (Santa Barbara /
  Montecito).
- Static site: Jekyll-style, hosted on GitHub Pages, repo `tsheasb/toddshearealtor`,
  `main` branch. DNS via Squarespace.
- `scripts/build.py` generates issue HTML pages, `rss.xml`, and updates
  `residency.html` / `index.html`.
- Mailchimp pulls the RSS feed on a biweekly cadence (Tuesdays, 9 AM Pacific),
  Audience ID `90c669fbd4`.
- Content (copy, structure, brand work) is written in the Claude Projects
  chat, not here. Your job starts once a finished post markdown file and its
  assets exist and need to be built and deployed.

## Standing rule: one editing path only

Previously, a separate agent (Kaya, on OpenClaw) handled deploy while content
was built elsewhere. That produced incidents: direct edits to generated files
(like a hand-patched `rss.xml`) that silently reverted the next time the
build ran, because the underlying script wasn't fixed.

**Kaya is fully retired from this repo as of Aug 19, 2026. She will not touch
it going forward.** You are the single owner of build, deploy, and Mailchimp
template state, end to end. Never hand-patch a generated output file
(`rss.xml`, `*.html` under `posts/`) to fix a bug. If a generated file is
wrong, fix the script that generates it (`scripts/build.py`), then
regenerate. If you're not sure whether something is generated or
hand-authored, check for a `# generated by build.py` type marker or ask
before editing.

## Build steps (every issue)

1. Confirm the post markdown file exists in `posts/` with correct frontmatter
   (`title`, `date`, `number`, `teaser`, `hero`, `hero_alt`).
2. Confirm all referenced images exist under `assets/posts/`.
3. Run `python3 scripts/build.py` from repo root.
4. Verify clean output — no errors, correct post count. If the build prints
   "Build stopped", fix the post markdown it names and rebuild (see "Layout v2
   and build guards" below). Never loosen the check.
5. Spot-check the generated `rss.xml`:
   - The new item is first, and its hero `<img>` is in `<content:encoded>`
     (Issue 07+: after the generated issue label and title).
   - `<description>` is the SHORT teaser, never the full body (see the RSS
     section below).
   - `<pubDate>` is well-formed, and the issue date is a Tuesday on the
     biweekly cadence.
6. Commit and push to `main`.

## RSS feed shape and the Mailchimp template's merge tags (corrected Aug 19, 2026)

**Superseded note:** an earlier version of this section said `<description>`
needed the full HTML body duplicated into it, and that the Mailchimp template
should read `*|RSSITEM:DESCRIPTION|*` for the main content. That diagnosis
was wrong and was itself the root cause of the Issue 02 (Aug 18, 2026) send
bug — `RSSITEM:DESCRIPTION` isn't even a documented Mailchimp merge tag, and
jamming full HTML into `<description>` also broke the inbox preview-text
snippet, which reads from the same field.

**Correct, current, live-verified setup:**

- `render_rss()` in `scripts/build.py` keeps `<description>` as the **short
  teaser** (`p['teaser']`) and puts the **full HTML body** in
  `<content:encoded>`, standard RSS convention. Verify this stays this way —
  don't let `<description>` grow the full body again.
- The live Mailchimp campaign template (`a2fb321312`) uses
  `*|RSSITEM:CONTENT_FULL|*` (full HTML, from `<content:encoded>`) for the
  main content block, and `*|RSSITEM:CONTENT_TEXT|*` (short plain text, from
  `<description>`) for the preheader/preview-text div. These are Mailchimp's
  actual documented tags — see https://mailchimp.com/help/rss-merge-tags/.
- Root-relative image paths (`/assets/...`) resolve fine on the live site but
  have no origin to resolve against inside an email. `render_rss()` rewrites
  `src="/..."` to absolute `SITE_URL` links specifically for the feed output
  — this is separate from `body_html`, which stays relative for the website.
- Known, deferred, cosmetic-only issue: `*|RSSITEM:PUBDATE:F j, Y|*` renders
  one day earlier than the real `<pubDate>` (verified via live test sends on
  Issues 02 and 03). Doesn't affect send timing, since Mailchimp's "is this
  new" check isn't driven by that formatted display string. Not yet fixed.

If you ever see `<description>` reverting to the full body, or the template
reverting to `RSSITEM:DESCRIPTION`, that's a regression — fix it back to the
setup above, never by hand-editing `rss.xml` or the live template ad hoc.

## Layout v2 and build guards (Issue 07 onward, Oct 2026 reskin)

- `render_post()` in `scripts/build.py` dispatches on front matter `number`.
  Issues 01 to 06 use `render_post_legacy` (framed Poppins graphic hero).
  Issue 07+ use `render_post_v2`: a title block generated from front matter, a
  full-bleed photo hero, and body photos that run full bleed
  (`.article--bleed`). A body image stays in the text column if its filename
  contains `-inset` or it is the House Radio cover. Change the layout in
  `build.py` and `css/reskin.css`, never in the generated HTML.
- Issue 07+ heroes are photos with no baked-in text (spec in
  `reference/brand-voice.md`). The title, number, and date come from front
  matter, so a front matter typo is now how an issue goes out wrong.
- `validate_posts()` stops the build for: a title without the
  `The SB Residency: ` prefix, a missing or duplicate `number`, an Issue 07+
  with no hero or with an em/en dash, and any `/assets/...` image that does not
  exist. Fix the markdown; do not weaken the check.
- For Issue 07+, `feed_header()` puts an issue label and title above the hero
  in `<content:encoded>`. The Mailchimp template therefore must NOT print its
  own title block, date line, or "Ready When You Are" block (the post carries
  its own), or they show twice. Keep the subject line on `*|RSSITEM:TITLE|*`.
  The template as set in Oct 2026 already follows this.
- Email photo width: the template card is 720px, and photos are edge to edge
  within it. That comes from `feed_bleed()` in `build.py`, which gives each
  photo-only paragraph an inline `padding:0`. Inline styles are what desktop
  Gmail honors reliably; do not move this into the template stylesheet. Photos
  cannot span the whole Gmail window in a standard email, and Todd decided on
  2026-10-22 to keep the 720px column. The House Radio cover and `-inset` photos
  stay in the padded column.
- Do not "fix" the template's content tag to `*|RSSITEM:CONTENT|*`. `CONTENT`
  is the short summary from `<description>`. The body is `CONTENT_FULL` and the
  preheader is `CONTENT_TEXT`, as above.
- `scripts/check.py` needs Playwright (`pip install playwright && playwright
  install chromium`) and now always includes the newest issue page.

## Changing the Mailchimp template

A normal issue needs no template change. The template is versioned at
`reference/mailchimp-template.html`; that file must match what Mailchimp serves.
To change it (each live step needs Todd's go-ahead in that moment):

1. Edit a copy of the file. Keep these tags: `*|RSSITEM:CONTENT_FULL|*` (body),
   `*|RSSITEM:CONTENT_TEXT|*` (preheader), `*|RSSITEM:TITLE|*` (`<title>` only),
   `*|LIST:ADDRESS|*`, `*|UNSUB|*`, and keep the BHHS compliance footer text.
2. Preview it locally with the real live feed substituted for the tags. For email,
   simulate what Mailchimp injects on every image
   (`style="max-width:100%;width:100%;display:inline..." class="mcRssImage"`).
3. Pause the campaign, `PUT /campaigns/a2fb321312/content` with `{"html": ...}`, and
   `GET` it back to confirm the stored HTML equals what was sent.
4. Send a test to Todd only (`POST .../actions/test`). A test pulls the newest item
   from the LIVE feed, so push any feed change first.
5. Resume the campaign. Confirm `status: sending` and that `last_sent` is unchanged.
6. Save the final served HTML back to `reference/mailchimp-template.html` and commit.

Todd opens the test in desktop Gmail, so his view of a test email is the real check.

## Mailchimp merge tag format

Mailchimp's RSS merge tags use **PHP date() format codes**, not Python
strftime codes. Example: `*|RSSITEM:PUBDATE:F j, Y|*` renders as
"September 2, 2026". A tag like `*|RSSITEM:PUBDATE:%B %d, %Y|*` will render
literally as broken text in the email, it will NOT error, it will just show
garbage to subscribers. Always verify merge tag syntax against Mailchimp's
own documentation before deploying a template change, never assume Python
conventions carry over.

Before resuming a paused campaign after any template edit, do a **send test /
preview** if the API allows it, or at minimum re-verify the rendered
`content:encoded` and template merge tags before letting the campaign go
live again.

## MLS listing photos — required before every Mailchimp send

FLEX MLS listing photos are served from `sparkplatform.com`, which
**hotlink-blocks** Mailchimp's email rendering. Every issue with Window
Shopping listings needs this step before the campaign sends:

1. Download the listing photos referenced in the post.
2. Upload them to Mailchimp File Manager.
3. Swap the `sparkplatform.com` URLs in the live post/RSS for the resulting
   `mcusercontent.com` URLs.

Photos already hosted in `/assets/posts/` (hero images, IG follow photos,
dashboard mockups, etc.) are unaffected and need no swap.
